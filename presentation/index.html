Introduction

Project overview

Odyssey is a custom C++ library for VEX V5 competition robots. It continuously tracks the robot's position — (x, y, heading) — and provides motion commands such as "drive to (24, 36) facing 90°".

About 600 lines of C++ Trigonometry and control theory Distributed as a library

The robot

A VEX V5 competition robot running PROS, a C++ environment for the V5 brain.

The task

During the autonomous period the robot moves without a driver. It must know its position to score consistently.

The result

An installable template that any team robot can use, with a documentation site.

Motivation

Why this project

The problem

Most autonomous routines run the motors for a fixed time or distance. A bump, a low battery, or a crooked start throws off the entire routine, because there is no position feedback.

The objective

A robot that determines its actual position and corrects toward target coordinates on every run.

  • Reliability in matches.The routine should perform consistently whether the start is exact or disturbed.
  • Understanding the system.Libraries such as LemLib and EZ-Template exist, but building it independently allows customization and an understanding of the underlying math.
  • Reuse across the team.A single template that installs on any robot.
Project goals

Goals defined at the start

How it works

Accumulating small arcs

Two free-spinning tracking wheels (one forward, one sideways) and an inertial sensor measure the robot's motion. Every 10 milliseconds:

  • Read how far each wheel rolled and how much the robot turned
  • Model that small motion as a slice of a circle, an arc
  • Rotate it into field coordinates and add it to the running total

This runs 100 times per second and produces a position estimate from geometry alone, without an external signal.

Readable code excerpts

Complex computation, simple interface

The heart of the tracker

// each 10ms tick: turn one tiny arc into a
// position change, then add it to the total
float avgTheta = pose.theta + dTheta / 2.0f;
pose.x += localY * cos(avgTheta)
        + localX * sin(avgTheta);
pose.y += localY * sin(avgTheta)
        - localX * cos(avgTheta);
pose.theta += dTheta;

Current capabilities

What Odyssey provides

Odometry

Arc-based tracking with any combination of wheels and IMU. Falls back to drive encoders, or to wheel-only heading if the IMU fails during a match.

PID motions

Turn to a heading or point, swing turns, and drive to a point, with tunable exit conditions and slew limiting.

Boomerang controller

moveToPose reaches a position and a final heading in one smooth arc.

Pure pursuit

Follow smooth paths drawn in a visual editor, loaded from the SD card.

Asynchronous motions

Start a motion, trigger another mechanism partway through, then wait for completion.

Driver control

Tank, arcade, and curvature drive with configurable exponential input curves.

Beyond a minimum product: Odyssey is distributed as an installable PROS template with versioned GitHub releases, an auto-updating depot, a continuous-integration build pipeline, and an MkDocs documentation website.

Obstacles and solutions

Obstacles encountered

No local compilation

The development laptop has no ARM toolchain, so the V5 code cannot be built locally. Solution: a GitHub Actions pipeline compiles every push in the cloud with ARM GCC 14, providing a build check on every change.

Two coordinate systems

The math uses radians (0 = east, counterclockwise); drivers use compass degrees (0 = north, clockwise). Mixing them produced incorrect motion. Solution: use one internal convention, document the conversion, and convert only at the interface.

Integrating AI output

AI suggestions often used LemLib conventions or the older PROS 3 API and did not compile or match the design. Solution: use it to understand concepts, then reimplement within the project's structure and API.

Error accumulation

A small heading error misdirects all later motion, so drift compounds (visible in the simulator with noise enabled). Solution: use the IMU for heading, average two wheels, and fall back to a secondary source if a sensor fails.

Testing and iteration

Testing and iteration

Odometry is only useful if it is accurate, so it was tested against physical measurements and adjusted until the reported position matched reality.

Diagnostic principle: drift while spinning indicates incorrect wheel offsets; drift while driving straight indicates incorrect wheel size. Separating the two made tuning systematic.
  • Square test.Drive a known 4 ft square, measure how far the robot ends from the start, and compare to the reported position.
  • Spin-in-place test.Rotate in place repeatedly and confirm the position barely changes, which isolates the tracking-wheel offsets.
  • Iterative PID tuning.Repeated commits adjusting gains until motions stopped overshooting and oscillating.
  • Simulator.A visual test bench to observe the estimate diverge without using the robot.
  • Automated checks.CI compiles every push; documentation builds in strict mode to catch broken links.

Future work

Future improvements

The current version meets its goals. Several improvements would form the next version, and some components would be rebuilt.

A larger change would be replacing the sensor handling with a Kalman filter that statistically combines the IMU, wheels, and the V5 GPS sensor, instead of using one source at a time.
  • Motion profiling.Trapezoidal or S-curve velocity for smoother, faster, more repeatable motions.
  • Expand the simulator.An off-robot path simulator and match replay tool, prototyped by this demonstration.
  • Automated unit tests.Test the math in isolation so a change cannot silently break tracking.
  • Kalman sensor fusion.Combine all sensors statistically rather than using fallback only.
  • More configurations.Simpler setup for teams with different sensor combinations.
